Log expenses into a Google Sheet by sending a voice note, text or receipt photo to a Slack DM.

## Code rules (set by Mauro)

- Small, single-responsibility files. Aim for under 100 lines. 150 lines is unacceptable.
- No barrel files: every `__init__.py` stays empty; import from the module that defines the thing.
- Orchestration files (wiring modules together) are welcome.
- Everything in the repo is in English: code, comments, tests, eval cases, docs, prompts and logs (decided 2026-10-25 by Mauro). Mauro's own Spanish values (headers, categories) live only in his gitignored `config.yaml`.

## Deployment notes (cheap always-on Linux server)

Estimates from general knowledge, NOT measured. Step 11 includes a benchmark on the real server.

- **No inbound ports needed** (Socket Mode). Firewall everything except SSH. Run as a non-root user, `chmod 600` the Google key and the env file, load secrets through the service manager's environment file, enable automatic security updates.
- **With local speech-to-text:** the model file is 547 MB and whisper.cpp needs roughly 1 to 1.5 GB of RAM with it loaded, so aim for 2 vCPU, 4 GB RAM, 20 GB disk (2 GB RAM plus swap may work). Without a GPU, transcription is much slower than the 13 s measured on the M4; a short voice note could take tens of seconds on 2 vCPUs. x86 or ARM both work; build whisper.cpp natively on the server. Smaller or more quantized models (`small`, `base`) trade accuracy for speed.
- **Without speech-to-text** (text and photos only) the process is mostly idle and 512 MB to 1 GB of RAM is enough.
- **A hosted transcription API** would allow a tiny server but sends audio to a third party. Not chosen; Anthropic has no audio input.
- A Docker image that builds whisper.cpp is planned for portability (step 11). It is for servers; on a Mac, Docker cannot use the GPU, so run natively there.

Flow: Slack DM event, then allowlist check and dedupe, then the thread is re-read (a reply in an already-logged thread stops here), then `bundle` (text + transcripts + images; a newest message with nothing to read gets a fixed answer), then `extract` (Claude), then `sanity`. If complete: `sheets.append`, then `sheets.read_row` reads the written row back, then a Slack thread reply shows what was recorded, for example `Logged in row 224: 05/10/2026 | $45.20 | Food | Market`. If the entry is incomplete: reply with a question in the thread. If the write fails: reply with the error and do not say it was logged.

### [x] 4. Extraction (Claude)

### [x] 8. Pipeline and entry point
`pipeline/bundle.py` (text + transcripts + images into one extraction input), `pipeline/handle_message.py` (orchestrator: allowlist, dedupe, bundle, extract, sanity, append, read the row back, send the confirmation or the follow-up question), `main.py` (wire and start; it already has the `init` subcommand and requires a subcommand, so add one that starts the bot, for example `run`, and keep `main.py` a thin dispatcher). The orchestrator calls `claim()` first and stops if it returns `False`; it calls `finish()` only after the append succeeded (the confirmation is sent after that) and `fail()` on any handled error. Call `stt.check.check_stt` at startup. Extraction is `extract.client.extract(..., today)` then `extract.sanity.check(result, categories, today)`; the thread becomes `Turn`s (bot messages as `author="bot"`, transcripts with `voice=True`). `today` is the day the thread's first message was sent, in the configured timezone (`today_in(timezone, now=<thread_root ts as a UTC datetime>)`), not the time the bot handles it: a note sent at 23:55 and handled after midnight, or caught up after sleep (step 10), keeps its day, and "yesterday" in the first message still means the day before it was sent when the user answers a question the next morning.
Sheets wiring: `open_worksheet` once at startup; per message `read_layout`, `read_categories(worksheet, layout.category, fallback)`, `read_examples` (convert each `DisplayedRow` to `extract.inputs.ExampleRow`; `sheets` does not import `extract`), `append_entry(day=result.day, ...)`, then `read_row`. `SheetsError` and `DedupeError` are handled errors. A write error can come after Google already stored the row (for example a timeout on the reply), so the error message must tell the user to check the sheet before resending.
Duplicate trap: re-reading a thread that already got a confirmation would extract the same expense again. A reply in a thread that already has a confirmation must never log another row (for example, reply that the entry is already logged).
